# LIVE MD 상세 페이지 연관 상품 노출 실험

| | |
|---|---|
| 대상 화면 | 상품 상세 페이지 (예: [`/products/567`](https://shop.novera.town/products/567) — 이한결 11.13 파자마 비디오콜) |
| 목적 | 같은 아티스트·같은 유형 상품으로의 유입을 만들어 LIVE MD 연계 매출과 교차 탐색을 올립니다 |
| 상태 | 초안 — [남은 결정 사항](#9-남은-결정-사항) 확인 필요 |
| 작성일 | 2026-11-10 (2026-11-11 측정 방식 변경) |

## 1. 요약

- LIVE MD는 한 아티스트가 **같은 회차에 여러 이벤트 상품을 동시에 판매**하는데, 상세 페이지에는 다른 상품으로 가는 길이 없어요.
- 그래서 상세 페이지에 모듈 두 개를 넣으려고 합니다.
  - **모듈 1 — 같은 아티스트의 다른 LIVE MD**: 구매 영역 바로 아래
  - **모듈 2 — LIVE MD 최신 상품**(1차 카테고리 기준 최신순): 상세 정보 하단
- 판매 중·판매 종료 상세 페이지 모두에 노출하고, 카드에는 판매 종료 상품도 함께 보여 줍니다.
- 두 모듈 모두 **기존 공개 API만으로 구현할 수 있어요**. 서버 작업은 필요 없습니다.
- 이번 실험은 **개선안을 전체 배포한 뒤, 배포 전 지표와 배포 후 지표를 비교**해서 측정합니다.
  서로 다른 시안을 나눠 보여 주는 A/B 테스트는 실험 환경을 구축한 뒤에 진행해요.
- 판정 지표는 **회차 내 교차 구매율** 하나로 고정하고, 모듈 클릭률은 진단 지표로 봅니다.

## 2. 배경

### 2.1 현재 상태 (2026-11-10 기준 실제 데이터)

`shop-api.novera.town` 공개 API로 확인한 LIVE MD 카탈로그입니다.

| 항목 | 값 |
|---|---|
| LIVE MD 상품 수 | 108개 |
| 아티스트 수 | 22팀 |
| 판매 회차 수 (아티스트 × 이벤트 날짜) | 38회차 |
| 상품이 2개 이상 동시에 열린 회차 | 33회차 (87%) |
| 회차당 상품 수 | 평균 2.8개 (1개 5회, 2개 8회, 3개 15회, 4개 9회, 6개 1회) |
| 회차 내 상품 가격이 모두 같은 회차 | 38회차 전부 |
| 가격대 | 7,400원 ~ 57,600원 (중앙값 17,800원) |
| 현재 판매 중인 LIVE MD | 0개 (모두 응모 마감) |

이한결의 경우 11.13 회차에 4종(파자마 비디오콜, 할리갈리 게임, 부채 꾸미기, FAN SIGN)이 모두 17,800원으로 동시에 열렸고, 그 전 10.14 회차에 2종이 있었습니다.

그런데 지금 상세 페이지에는 상단의 아티스트명 링크 말고는 다른 상품으로 가는 경로가 없어요. 연관 상품, 추천, 같은 회차 상품 영역이 모두 없습니다.

### 2.2 팬덤 특성으로 본 문제

**① 팬은 쇼핑몰이 아니라 상품 하나로 들어와요.**
LIVE MD 구매자는 아티스트 공지, SNS, 팬 커뮤니티에 걸린 링크를 타고 특정 상품 상세로 바로 들어옵니다. 홈이나 카테고리를 거치지 않기 때문에, 상세 페이지가 알려 주지 않으면 같은 회차에 다른 이벤트가 있다는 사실 자체를 모를 수 있어요. 이 유입에서는 상세 페이지가 사실상 유일한 진열대입니다.

**② 구매 동기는 상품이 아니라 아티스트예요.**
팬이 사는 것은 "파자마 비디오콜"이 아니라 "한결과 만날 기회"입니다. 같은 아티스트의 다른 이벤트는 대체재가 아니라 **또 하나의 만날 기회**라서, 일반 커머스의 유사 상품 추천보다 관련성이 훨씬 높아요. 한 이벤트에 관심을 보인 팬은 나머지 이벤트의 가장 유력한 잠재 구매자입니다.

**③ 응모형 상품이라 여러 개를 사는 것이 자연스러워요.**
LIVE MD는 당첨자 수가 정해진 응모 상품입니다(567번은 당첨자 10명, 중복 구매 가능, 최대 500개). 팬은 당첨 확률을 높이려고 이미 여러 장을 사요. 이벤트마다 경험이 달라서(영상통화, 팬사인, 게임, 꾸미기) "전부 응모"하려는 수요도 있습니다. 회차 내 가격이 전부 같아 추가 구매의 심리적 장벽도 낮아요.

**④ 판매 기간이 짧아 놓치면 끝이에요.**
회차 판매 기간은 3~4일 수준입니다(567번은 11/5 등록, 11/8 마감). 팬이 다른 이벤트를 마감 뒤에 알게 되면 그 매출은 되찾을 수 없어요. 발견을 팬의 탐색에 맡기기에는 기간이 너무 짧습니다.

**⑤ 글로벌 팬 대상이라 상세가 길어요.**
안내문이 한·일·영 3개 국어로 반복되어 상세 영역이 깁니다. 하단에만 모듈을 두면 도달률이 낮을 가능성이 커요. 같은 아티스트 모듈을 구매 영역 바로 아래에 두려는 이유입니다.

**⑥ 종료된 상세 페이지는 막다른 길이에요.**
마감 뒤에도 공유된 링크로 유입은 계속됩니다. 지금은 "품절" 버튼만 보이고 갈 곳이 없어요. 이한결은 현재 6종이 모두 종료 상태입니다.

**⑦ 지난 이벤트 목록은 "다음에도 열린다"는 신호가 돼요.**
22팀 중 13팀이 2회차 이상 진행했습니다. 종료된 이벤트를 함께 보여 주면 이 아티스트가 이벤트를 반복해서 연다는 것을 알릴 수 있고, 이번에 놓친 팬에게 다시 방문할 기대를 줄 수 있어요. 판매 종료 상품을 카드에 포함하는 이유입니다.

### 2.3 주의할 점: 매출이 늘지 않고 나뉘기만 할 수 있어요

팬의 예산이 정해져 있다면, 한 이벤트에 5장 넣던 팬이 여러 이벤트에 나눠 넣을 뿐 총액은 그대로일 수 있습니다. 이 경우 교차 구매율은 오르지만 매출은 늘지 않아요. 그래서 교차 구매율과 **구매자당 결제액**을 반드시 같이 봅니다([6. 지표](#6-지표)).

## 3. 가설

모든 가설은 배포 전 회차의 지표와 비교해서 확인합니다.

| | 가설 | 확인 지표 |
|---|---|---|
| H1 | 구매 영역 아래에 같은 아티스트의 다른 LIVE MD를 보여 주면, 같은 회차 안에서 2종 이상을 구매하는 구매자 비율이 배포 전보다 오릅니다 | 회차 내 교차 구매율 |
| H2 | 교차 구매는 예산 재분배가 아니라 추가 지출로 이어집니다 | 구매자당 결제액, 방문자당 매출 |
| H3 | 상세 하단의 LIVE MD 최신 상품 모듈은 다른 아티스트 이벤트로의 탐색을 만듭니다 | 모듈 2 클릭률, 타 아티스트 상세 조회율 |
| H4 | 판매 종료 상세 페이지에 모듈을 두면 이탈이 줄고 판매 중 상품으로 유입됩니다 | 종료 페이지 이탈률, 판매 중 상품 도달률 |
| H5 | 판매 종료 카드를 함께 보여도 원 상품 구매를 방해하지 않습니다 | 원 상품 구매 전환율 (가드레일) |

H3는 팬이 여러 아티스트를 동시에 좋아한다는 전제에 기대고 있어요. 그런데 LIVE MD 팬덤에서 이 전제가 성립하는지는 아직 근거가 없습니다. 이번 실험에서 처음 확인하는 항목이에요.

## 4. 노출 방안

### 4.1 검토한 위치

| 위치 | 장점 | 단점 | 채택 |
|---|---|---|---|
| **구매 영역 바로 아래** (옵션·구매 버튼 아래, 상품 정보 탭 위) | 구매 결정 시점에 보임. 도달률 높음 | 구매 버튼과 가까워 주의가 분산될 수 있음 | 이번 배포 — 모듈 1 |
| **상세 정보 하단** | 구매 흐름을 방해하지 않음 | 3개 국어 안내문 때문에 도달률이 낮음 | 이번 배포 — 모듈 2 |
| **장바구니 담기 직후 바텀시트** | 구매 의도가 가장 높은 순간. 담기 전환을 방해하지 않음 | 담은 사람에게만 보임. 판매 종료 페이지에는 적용 불가 | 추후 A/B 테스트 후보 |
| 옵션 영역 안 "다른 이벤트도 함께 담기" | 한 번에 여러 이벤트 담기 가능 | 상품마다 입력 정보 5개가 따로 필요해 구조 변경이 큼 | 후속 검토 |
| 장바구니 페이지 | 구현이 단순함 | 결제 직전이라 이탈 위험. 바로 구매 경로는 거치지 않음 | 후속 검토 |

### 4.2 모듈 1 — 같은 아티스트의 다른 LIVE MD

- **위치**: 구매 영역 바로 아래
- **제목**: `{아티스트명}의 다른 LIVE MD` (예: 한결의 다른 LIVE MD)
- **형태**: 가로 스크롤 카드. 모바일 기준 2.3장이 보이게 해서 더 있다는 것을 알 수 있게 합니다
- **대상**: 같은 아티스트(`brand.id`)의 LIVE MD 상품. 현재 보고 있는 상품은 제외해요
- **정렬**: ① 판매 중(마감 임박순) → ② 판매 종료(최신순)
- **최대 개수**: 10개
- **카드 구성**: 썸네일, 이벤트명, 가격, 상태
  - 판매 중: `D-2` 또는 `오늘 마감` 배지
  - 판매 종료: `응모 종료` 배지, 썸네일을 흐리게 처리
- **이벤트명 표기**: 상품명이 `[11.13 할리갈리 게임] 이한결(LEE HAN GYUL) 1st Mini Album [NOISE] MEET & CALL EVENT`처럼 대괄호 안쪽만 달라요. 말줄임이 걸려도 **대괄호 부분은 반드시 전부 보이게** 합니다
- **다른 상품이 없을 때**: 구좌 자체를 노출하지 않습니다 ([4.5 엣지 케이스](#45-엣지-케이스))

### 4.3 모듈 2 — LIVE MD 최신 상품

- **위치**: 상세 정보 하단 (배송/교환/반품 안내 뒤)
- **제목**: `LIVE MD 최신 이벤트`
- **형태**: 2열 그리드 또는 가로 스크롤 ([남은 결정 사항](#9-남은-결정-사항))
- **대상**: 1차 카테고리 LIVE MD(`PCTGY3`) 전체, 최신순
- **중복 상품 제외**: 모듈 1의 히어로 노출 구간에 이미 나온 상품은 모듈 2에서 뺍니다 ([4.5 엣지 케이스](#45-엣지-케이스))
- **최대 개수**: 10개
- **카드 구성**: 모듈 1과 같되 아티스트명을 추가합니다
- **알아 둘 점**: 한 회차가 3~4종씩 연속으로 등록되어 최신순에서는 한 아티스트가 카드 여러 장을 차지해요. 결과에서 쏠림이 보이면 "회차당 카드 1장"으로 묶는 안을 후속으로 검토합니다

### 4.4 판매 종료 처리

- **판매 종료 상세 페이지**: 판매 중 페이지와 똑같이 두 모듈을 노출합니다. 정렬 규칙상 판매 중 상품이 앞에 와요
- **판매 종료 카드**: 판매 중 페이지에도 함께 노출합니다. 배지와 흐림 처리로 상태를 구분하고, 누르면 종료된 상세 페이지로 이동해요
- **전부 종료된 경우**: 지금처럼 LIVE MD 전체가 마감된 시기에는 모듈이 종료 카드로만 채워져요. 이때 클릭이 막다른 길로 이어지지 않는지 가드레일로 봅니다

### 4.5 엣지 케이스

여기서 **히어로 노출 구간**은 모듈 1에서 스크롤하지 않아도 처음부터 보이는 카드를 말해요(모바일 기준 앞 3장). 정확한 장수는 [남은 결정 사항](#9-남은-결정-사항)에서 확정합니다.

| 상황 | 처리 |
|---|---|
| 같은 아티스트의 다른 LIVE MD 상품이 없음 | 모듈 1 구좌를 노출하지 않습니다. 제목과 여백까지 모두 빼서 빈 공간이 남지 않게 해요 |
| 두 모듈의 상품이 겹침 | 모듈 1의 히어로 노출 구간에 나온 상품은 모듈 2(하단 같은 카테고리 모듈)에서 제외합니다. 구현이 가능한 경우에 적용하고, 어렵다면 중복을 허용해요 |
| 중복을 빼고 나니 모듈 2에 남는 상품이 없음 | 모듈 2 구좌를 노출하지 않습니다 |
| 현재 보고 있는 상품 | 두 모듈 모두에서 제외합니다 |
| 같은 아티스트의 다른 상품이 전부 판매 종료 | 모듈 1을 그대로 노출하고 `응모 종료` 배지로 구분합니다 |
| 같은 아티스트가 LIVE MD가 아닌 상품(ALBUM, MD)도 가지고 있음 | 모듈 1에는 LIVE MD 상품만 보여 줍니다 |
| 목록 조회가 실패하거나 늦어짐 | 해당 구좌를 노출하지 않습니다. 구매 영역이 밀리지 않도록 자리를 미리 잡아 두지 않아요 |

현재 데이터 기준으로 모듈 1이 노출되지 않는 경우는 단일 상품 회차 5개와, 등록 상품이 1종뿐인 아티스트입니다.

### 4.6 구현 범위 — 서버 작업 불필요

두 모듈 모두 이미 열려 있는 공개 API로 조회돼요. 실제 호출로 확인했습니다.

| 모듈 | 요청 | 확인 결과 |
|---|---|---|
| 모듈 1 | `GET /v1/products?brandId={brand.id}` | `brandId=88` → 이한결 6종 반환 |
| 모듈 2 | `GET /v1/products?category=PCTGY3` | LIVE MD 108종, 최신순 반환 |

- 목록 응답에 `isSelling`, `saleEndDate`, `price`, `mainImageId`, `brand`, `badges`가 들어 있어 카드에 필요한 값이 모두 있어요
- 판매 중 우선 정렬, 현재 상품 제외, 중복 상품 제외는 프런트에서 처리합니다
- `category` 파라미터는 문서가 아니라 호출 결과로 확인한 것이에요. 개발 착수 전에 프런트 담당자 확인이 필요합니다
- 어센트, 코스모시, 오메가엑스는 LIVE MD가 아닌 상품도 가지고 있어요. `brandId`만으로 조회하면 일반 상품이 섞이므로 `category=PCTGY3`와 함께 걸거나 프런트에서 걸러야 합니다

## 5. 실험 설계

### 5.1 검증 방식 — 배포 전후 비교

이번 실험은 개선안(모듈 1 + 모듈 2 상세 기본 노출)을 **모든 방문자에게 배포**하고, 배포 전 지표와 배포 후 지표를 비교합니다.

이렇게 정한 배경은 다음과 같아요.

- 지금은 방문자를 나눠 서로 다른 화면을 보여 줄 실험 환경이 없습니다
- 서로 다른 시안을 비교하는 A/B 테스트는 실험 환경을 구축한 뒤에 진행하기로 했어요
- 서버 작업 없이 프런트 배포만으로 바로 시작할 수 있습니다

이 방식으로 알 수 있는 것과 없는 것을 미리 구분해 둡니다.

| 구분 | 내용 |
|---|---|
| 알 수 있는 것 | 모듈이 실제로 쓰이는지(도달·클릭), 클릭이 구매로 이어지는지, 교차 구매율과 결제액이 지난 회차 범위와 비교해 어느 수준인지 |
| 알 수 없는 것 | 지표 변화가 모듈 덕분인지, 아티스트·가격·상품 구성이 달라서인지. 같은 시기의 비교 대상이 없어서 원인을 단정할 수 없어요 |

그래서 이번 결과는 "효과가 확인됐다"가 아니라 **"방향이 맞는지"** 를 판단하는 근거로 씁니다. 원인까지 확인하는 일은 추후 A/B 테스트에서 해요.

### 5.2 단계

| 단계 | 내용 | 개발 |
|---|---|---|
| 0. 배포 전 기준선 확보 | 지난 회차의 교차 구매율, 구매자당 결제액 등을 뽑고, 기존 이벤트 로깅 상태를 확인합니다 | 없음 (데이터 추출) |
| 1. 전체 배포 후 측정 | 개선안을 전체 배포하고, 배포 후 한 팀의 회차를 측정해 기준선과 비교합니다 | 프런트만 |
| 2. 시안 A/B 테스트 (추후) | 실험 환경을 구축한 뒤, 담기 직후 바텀시트 등 다른 시안을 나눠서 비교합니다 | 실험 환경 필요 |

0단계는 다음 회차가 열리기 전인 지금 바로 진행할 수 있어요.

### 5.3 비교 기준

배포 후에 측정하는 팀과 배포 전 회차의 아티스트는 서로 다를 수밖에 없습니다. 같은 아티스트끼리 맞춰 비교할 수 없으니, 배포 전 회차 전체를 하나의 기준선으로 써요.

- **배포 전 기준선**: 지난 LIVE MD 회차 중 상품이 2종 이상이었던 회차(현재 33회차)의 지표를 회차별로 뽑아 평균과 범위(최저~최고)를 정리합니다
- **배포 후 값**: 측정 대상 한 팀의 회차 값을 기준선의 평균·범위와 나란히 놓고 봅니다
- **참고용 비교군**: 기준선 안에서 측정 팀과 상품 수·가격대가 비슷한 회차를 따로 표시해 함께 봐요
- **배포 일시 기록**: 전후를 가르는 기준이므로 배포 일시를 문서에 남깁니다

### 5.4 대상과 기간

- **대상**: LIVE MD 상세 페이지 방문자 (판매 중·판매 종료 모두). 판정은 판매 중 상품 방문자 기준으로 하고, 판매 종료 페이지는 따로 봅니다
- **측정 기간**: 배포 후 **한 팀의 한 회차**를 기준으로 잡습니다. 그 회차의 판매 시작부터 마감까지 전체를 봐요
- **측정 대상 팀의 조건**: 동시에 판매하는 상품이 2종 이상이어야 합니다. 1종뿐이면 모듈 1이 노출되지 않아 측정할 수 없어요
- **분석 단위**: 회차 안에서의 방문자·구매자. 팬이 주문을 나눠 넣을 수 있어서 주문 단위가 아니라 **구매자 × 회차** 단위로 봐요
- **중간 판단 금지**: 회차가 끝나기 전에 결과를 보고 결론 내리지 않습니다. 마감 직전에 구매가 몰리기 때문이에요

### 5.5 결과를 읽는 기준

한 팀의 한 회차만 측정하므로 통계적 유의성은 따지지 않습니다. 대신 배포 전 범위와 비교해 신호의 세기를 나눠 읽어요.

| 배포 후 값의 위치 | 해석 |
|---|---|
| 배포 전 최고값보다 높음 | 강한 신호. 지난 어떤 회차에서도 나온 적 없는 수준이에요 |
| 배포 전 평균보다 높고 최고값 이하 | 약한 신호. 방향은 맞지만 아티스트 차이일 가능성이 남아 있어요 |
| 배포 전 평균 이하 | 신호 없음. 모듈 도달률과 클릭률부터 확인합니다 |

측정이 한 팀에 그치는 만큼, 이후 회차에서도 같은 지표를 계속 쌓아 추세를 확인합니다.

## 6. 지표

### 6.1 지표 구조

클릭률과 연계 구매를 둘 다 보되 역할을 나눕니다. **판정은 교차 구매율로** 하고, 클릭률은 **왜 그런 결과가 나왔는지 설명하는 지표**로 써요. 이렇게 나누는 이유는 다음과 같습니다.

- 모듈 클릭률은 배포 전에는 모듈이 없어서 값이 존재하지 않아요. 배포 전후를 비교하는 지표가 될 수 없습니다
- 클릭은 많은데 구매는 안 늘 수 있어요. 판정 지표가 둘이면 결과가 엇갈릴 때 결론을 내릴 수 없습니다
- 실험 목표가 연계 매출이므로 판정은 구매로 합니다

### 6.2 판정 지표 (1개)

| 지표 | 정의 |
|---|---|
| **회차 내 교차 구매율** | 한 회차에서 LIVE MD를 구매한 사람 중, 그 회차 안에서 서로 다른 LIVE MD 상품을 2종 이상 구매한 사람의 비율 |

주문 DB만 있으면 지난 회차 값도 뽑을 수 있어서 배포 전후 비교가 가능합니다.

### 6.3 매출 확인 지표

교차 구매가 추가 매출인지, 재분배인지 가려내는 지표입니다. 모두 주문 DB에서 배포 전 값을 뽑을 수 있어요.

| 지표 | 정의 | 보는 이유 |
|---|---|---|
| 구매자당 결제액 | 회차 내 LIVE MD 결제액 합계 ÷ 구매자 수 | 교차 구매율만 오르고 이 값이 그대로면 재분배예요 |
| 방문자당 LIVE MD 매출 | LIVE MD 결제액 합계 ÷ LIVE MD 상세 방문자 수 | 전환율 변화까지 포함한 최종 매출 효과 |
| 구매자당 구매 상품 종류 수 | 회차 내 서로 다른 LIVE MD 상품 수의 평균 | 교차 구매의 깊이 |
| 구매자당 구매 수량 | 회차 내 LIVE MD 총 수량의 평균 | 종류는 늘고 수량은 그대로인지 확인 |

구매자당 결제액은 회차마다 상품 가격이 달라 그대로 비교하기 어려워요. 상품 가격으로 나눈 값(구매자당 구매 수량)도 함께 봅니다.

### 6.4 선행 지표

구매보다 빨리 쌓여서 방향을 먼저 확인할 수 있어요. 다만 **배포 전에 상세 조회·담기 이벤트가 상품 ID와 함께 남아 있어야만** 배포 전 값과 비교할 수 있습니다. 남아 있지 않다면 배포 후 값만 기록해요.

| 지표 | 정의 | 배포 전 비교 |
|---|---|---|
| 교차 탐색률 | LIVE MD 상세 방문자 중 같은 세션에서 다른 LIVE MD 상세를 본 비율 | 기존 로깅이 있을 때만 가능 |
| 교차 담기율 | LIVE MD 상세 방문자 중 서로 다른 LIVE MD 2종 이상을 장바구니에 담은 비율 | 기존 로깅이 있을 때만 가능 |

### 6.5 진단 지표 (배포 후에만)

모듈 설계를 고치는 데 씁니다.

| 지표 | 정의 |
|---|---|
| 모듈 도달률 | 상세 방문자 중 모듈이 화면에 들어온 비율 (모듈 1, 2 각각) |
| 모듈 클릭률 | 모듈이 보인 방문자 중 카드를 누른 비율 (모듈 1, 2 각각) |
| 카드 순서별 클릭 분포 | 몇 번째 카드가 눌리는지 |
| 판매 종료 카드 클릭 비중 | 전체 카드 클릭 중 판매 종료 카드의 비율 |
| 클릭 후 구매 전환율 | 카드를 눌러 도착한 상품을 구매한 비율 |
| 모듈 2 타 아티스트 구매율 | 모듈 2를 거쳐 다른 아티스트 상품을 구매한 비율 (H3 확인) |

### 6.6 가드레일 지표

배포 전 기준선과 비교합니다. 하나라도 기준을 벗어나면 원인을 먼저 확인하고, 필요하면 모듈을 내려요. 회차 간 편차가 커서 구체적인 기준값은 0단계에서 기준선을 본 뒤 확정합니다.

| 지표 | 정의 | 기준 |
|---|---|---|
| 원 상품 구매 전환율 | 처음 들어온 상품을 구매한 방문자 비율 | 배포 전 범위의 최저값보다 낮아지지 않아야 해요 |
| 원 상품 담기율 | 처음 들어온 상품을 장바구니에 담거나 바로 구매를 누른 비율 | 배포 전 범위의 최저값보다 낮아지지 않아야 해요 |
| 구매자당 구매 수량 | 6.3과 같음 | 배포 전 범위의 최저값보다 낮아지지 않아야 해요 |
| 결제 완료율 | 주문서 진입 대비 결제 완료 비율 | 배포 전 범위의 최저값보다 낮아지지 않아야 해요 |
| 판매 종료 카드 클릭 후 이탈률 | 판매 종료 카드를 누른 뒤 바로 나간 세션 비율 | 판매 중 카드 클릭 후 이탈률의 1.5배 이내 |
| 주문 취소·문의 건수 | 주문 1,000건당 취소 요청과 "잘못 응모" 유형 문의 건수 | 배포 전보다 늘지 않아야 해요 |
| 페이지 성능 | 상세 페이지 LCP, CLS | LCP 악화 200ms 이내, CLS 0.1 이하 유지 |

원 상품 구매 전환율·담기율·결제 완료율은 방문 기록이 필요해서, 6.4와 마찬가지로 기존 로깅이 있어야 배포 전 값과 비교할 수 있어요.

주문 취소·문의를 보는 이유는 LIVE MD가 취소 불가 상품이기 때문입니다. 이벤트 카드가 서로 비슷해서 팬이 의도와 다른 이벤트에 응모하면 바로 고객 응대 문제가 돼요.

### 6.7 판정 기준

| 결과 | 결정 |
|---|---|
| 교차 구매율이 배포 전 평균보다 높고, 구매자당 구매 수량이 줄지 않았고, 가드레일 통과 | 모듈을 유지합니다. 이후 회차에서 추세를 계속 확인해요 |
| 교차 구매율은 높지만 구매자당 구매 수량이 그대로 | 재분배로 판단합니다. 매출 효과는 없지만 가드레일을 통과하면 유지해요 |
| 교차 탐색률·클릭률은 높은데 교차 구매율은 평균 이하 | 발견은 되지만 구매로 못 넘어가는 상태예요. 응모 정보 재입력 등 구매 단계의 마찰을 확인합니다 |
| 가드레일을 벗어남 | 모듈을 내리거나 위치를 아래로 옮깁니다. 판매 종료 카드를 빼는 안도 검토해요 |
| 모듈 도달률·클릭률 자체가 낮음 | 위치나 카드 구성 문제로 보고 모듈을 고칩니다 |

어떤 결과든 원인까지 확인된 것은 아니므로, 추후 A/B 테스트에서 다시 검증합니다.

## 7. 이벤트 로깅

기존 GA4·Amplitude에 아래 이벤트를 추가합니다.

| 이벤트 | 시점 | 속성 |
|---|---|---|
| `related_module_view` | 모듈이 화면에 50% 이상 들어왔을 때 (세션당 모듈별 1회) | `module`(artist/category), `source_product_id`, `source_is_selling`, `item_count`, `selling_item_count` |
| `related_item_click` | 카드를 눌렀을 때 | 위 속성 + `target_product_id`, `target_brand_id`, `target_is_selling`, `rank`, `is_same_round` |

**배포 전에 반드시 확인할 기존 이벤트**는 다음과 같아요. 배포 전 값은 나중에 되살릴 수 없기 때문에, 부족하면 모듈 배포보다 로깅 보강을 먼저 합니다.

- 상품 상세 조회, 장바구니 담기, 결제 완료 이벤트가 **상품 ID와 함께** 남고 있는지
- 결제 완료 이벤트에 주문 내 상품 목록과 금액이 들어 있는지

교차 구매율과 결제액은 이벤트가 부족해도 주문 DB에서 계산할 수 있습니다.

## 8. 리스크

| 리스크 | 대응 |
|---|---|
| 아티스트·가격·상품 구성 차이를 모듈 효과로 착각할 수 있어요 | 결과를 "방향 확인"으로만 해석합니다. 상품 수·가격대가 비슷한 회차를 참고용으로 함께 보고, 원인은 추후 A/B 테스트에서 확인해요 |
| 한 팀만 측정해서 그 팀의 팬덤 특성이 결과를 좌우할 수 있어요 | 이후 회차에서도 같은 지표를 계속 쌓아 추세를 봅니다 |
| 배포 전 방문 데이터가 없으면 선행 지표와 일부 가드레일을 비교할 수 없어요 | 0단계에서 기존 로깅을 먼저 확인하고, 부족하면 로깅을 보강한 뒤 배포합니다 |
| 판매 종료 카드가 많아 모듈이 "살 수 없는 상품 목록"처럼 보일 수 있어요 | 판매 중 우선 정렬, 배지와 흐림 처리. 판매 종료 카드 클릭 비중과 이탈률로 확인합니다 |
| 지금처럼 LIVE MD가 전부 마감된 시기에는 모듈이 종료 카드로만 채워져요 | 판정은 판매 중 상품 방문자 기준으로만 합니다. 전부 종료된 시기의 노출 방식은 [남은 결정 사항](#9-남은-결정-사항)에서 정해요 |
| 구매 버튼 근처 모듈이 원 상품 구매를 방해할 수 있어요 | 원 상품 전환율 가드레일로 확인하고, 벗어나면 위치를 내립니다 |
| 비슷한 카드 때문에 다른 이벤트에 잘못 응모할 수 있어요 | 대괄호 이벤트명 전체 노출, 취소·문의 가드레일 |
| 상품마다 응모 정보 5개(이름, 생년월일, 전화번호, 카카오톡 ID, 이메일)를 다시 입력해야 해서 교차 구매가 중간에 끊길 수 있어요 | 클릭 후 구매 전환율로 확인합니다. 낮으면 직전 입력값 자동 채움을 후속 과제로 올려요 |
| 모듈 2가 다른 아티스트로 팬을 보내 원 아티스트 매출이 줄어들 수 있어요 | 원 상품 전환율 가드레일, 모듈 2 클릭 후 원 상품 복귀율을 확인합니다 |

## 9. 남은 결정 사항

| # | 항목 | 제안 |
|---|---|---|
| 1 | 히어로 노출 구간을 몇 장으로 볼지 | 모듈 1의 앞 3장 (모바일에서 스크롤 없이 보이는 범위) |
| 2 | 중복 상품 제외를 프런트에서 구현할 수 있는지 | 프런트 담당자 확인이 필요합니다. 어렵다면 중복을 허용해요 |
| 3 | 측정 대상 팀 | 배포 후 처음 열리는, 상품 2종 이상인 팀의 회차 |
| 4 | 모듈 2 형태 | 가로 스크롤 (페이지 길이를 더 늘리지 않음) |
| 5 | LIVE MD가 전부 마감된 시기에 모듈을 그대로 노출할지 | 노출하되 제목을 `지난 LIVE MD`로 바꿔요 |
| 6 | LIVE MD가 아닌 상품(ALBUM, MD) 상세에도 같은 모듈을 넣을지 | 이번 범위에서는 제외하고, LIVE MD 결과를 본 뒤 결정해요 |
| 7 | 가드레일 기준값 | 0단계 기준선을 본 뒤 확정합니다 |
| 8 | 기존 구매·조회 이벤트 로깅 수준 | 배포 전 필수 확인 항목입니다. 프런트 담당자 확인이 필요해요 |

## 10. 결정 이력

| 항목 | 결정 |
|---|---|
| 모듈 1 위치 | 구매 영역 바로 아래, 같은 아티스트 상품 |
| 모듈 2 위치와 기준 | 상세 정보 하단, 2차가 아닌 1차 카테고리(LIVE MD) 기준 최신순 |
| 판매 종료 페이지 | 판매 중 페이지와 똑같이 모듈 노출 |
| 판매 종료 상품 | 카드에 함께 노출 (추후 오픈 가능성을 보여 주기 위함) |
| 아티스트의 다른 상품이 없을 때 | 모듈 1 구좌 미노출 |
| 두 모듈의 상품이 겹칠 때 | 가능하다면 모듈 1 히어로 노출 구간과 겹치는 상품을 모듈 2에서 제외 |
| 개발 범위 | 서버 작업 없이 프런트만 |
| 지표 | 연계 구매와 클릭률 둘 다 확인. 판정은 교차 구매율, 클릭률은 진단 |
| 측정 방식 | 개선안 전체 배포 후 배포 전후 지표 비교 (2026-11-11 변경) |
| 비교 기준 | 배포 전 회차 전체를 기준선으로 사용. 측정 팀과 아티스트가 다를 수밖에 없음 |
| 측정 기간 | 배포 후 한 팀의 한 회차 |
| 시안 A/B 테스트 | 실험 환경을 구축한 뒤 진행 |
