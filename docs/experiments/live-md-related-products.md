# [PRD] 상세 페이지 연관 상품 노출 실험

| | |
|---|---|
| 대상 화면 | 상품 상세 페이지 — 모든 카테고리 (예: [`/products/567`](https://shop.novera.town/products/567) — 이한결 11.13 파자마 비디오콜) |
| 목적 | 같은 아티스트·같은 유형 상품으로의 유입을 만들어 LIVE MD 연계 매출과 교차 탐색을 올립니다 |
| 상태 | 진행 중 — 1차 배포 완료, 최종 UI 핸드오프 중. [남은 결정 사항](#9-남은-결정-사항) 확인 필요 |
| 작성일 | 2026-11-10 (11-11 측정 방식 변경, 11-12 최종 UI·배포 현황 반영) |
| 디자인 | [Figma — 상품 상세_PDP ⎯ 연관 상품](https://www.figma.com/design/nZLePLLrY5Yh9cLf7ZSHuk/-NOVERA-shop--Handoff?node-id=39-108195) |

## 1. 요약

- LIVE MD는 한 아티스트가 **같은 회차에 여러 이벤트 상품을 동시에 판매**하는데, 상세 페이지에는 다른 상품으로 가는 길이 없어요.
- 그래서 상세 페이지에 모듈 두 개를 넣습니다.
  - **모듈 1 — 같은 아티스트의 다른 상품(LIVE MD + MD 전 상품 포함)**: 구매 영역 바로 아래
  - **모듈 2 — 같은 1차 카테고리의 최신 상품**(LIVE MD 상세에서는 LIVE MD 최신 상품): 상세 정보 하단
- LIVE MD뿐 아니라 **모든 카테고리의 상품 상세**에 적용합니다. 1차 배포는 이미 나갔어요.
- 판매 중·판매 종료 상세 페이지 모두에 노출하고, 카드에는 판매 종료 상품도 SOLD OUT 표시로 함께 보여 줍니다.
- 두 모듈 모두 **기존 공개 API만으로 구현했어요**. 다만 판매 중 우선 정렬과 중복 상품 제외는 서버 작업이 필요해서 결정을 기다리고 있습니다.
- 이번 실험은 **개선안을 전체 배포한 뒤, 배포 전 지표와 배포 후 지표를 비교**해서 측정합니다.
  서로 다른 시안을 나눠 보여 주는 A/B 테스트는 실험 환경을 구축한 뒤에 진행해요.
- 판정 지표는 **회차 내 교차 구매율** 하나로 고정하고, 모듈 클릭률은 진단 지표로 봅니다.

## 2. 배경

### 2.1 현재 상태 (2026-11-10 기준 실제 데이터)

`shop-api.novera.town` 공개 API로 확인한 LIVE MD 카탈로그입니다.

| 항목 | 값 |
|---|---|
| LIVE MD 상품 수 | 108개 |
| 아티스트 수 | 22팀 |
| 판매 회차 수 (아티스트 × 이벤트 날짜) | 38회차 |
| 상품이 2개 이상 동시에 열린 회차 | 33회차 (87%) |
| 회차당 상품 수 | 평균 2.8개 (1개 5회, 2개 8회, 3개 15회, 4개 9회, 6개 1회) |
| 회차 내 상품 가격이 모두 같은 회차 | 38회차 전부 |
| 가격대 | 7,400원 ~ 57,600원 (중앙값 17,800원) |
| 현재 판매 중인 LIVE MD | 0개 (모두 응모 마감) |

이한결의 경우 11.13 회차에 4종(파자마 비디오콜, 할리갈리 게임, 부채 꾸미기, FAN SIGN)이 모두 17,800원으로 동시에 열렸고, 그 전 10.14 회차에 2종이 있었습니다.

모듈을 넣기 전의 상세 페이지에는 상단의 아티스트명 링크 말고는 다른 상품으로 가는 경로가 없었어요. 연관 상품, 추천, 같은 회차 상품 영역이 모두 없었습니다.

### 2.2 팬덤 특성으로 본 문제

**① 팬은 쇼핑몰이 아니라 상품 하나로 들어와요.**
LIVE MD 구매자는 아티스트 공지, SNS, 팬 커뮤니티에 걸린 링크를 타고 특정 상품 상세로 바로 들어옵니다. 홈이나 카테고리를 거치지 않기 때문에, 상세 페이지가 알려 주지 않으면 같은 회차에 다른 이벤트가 있다는 사실 자체를 모를 수 있어요. 이 유입에서는 상세 페이지가 사실상 유일한 진열대입니다.

**② 구매 동기는 상품이 아니라 아티스트예요.**
팬이 사는 것은 "파자마 비디오콜"이 아니라 "한결과 만날 기회"입니다. 같은 아티스트의 다른 이벤트는 대체재가 아니라 **또 하나의 만날 기회**라서, 일반 커머스의 유사 상품 추천보다 관련성이 훨씬 높아요. 한 이벤트에 관심을 보인 팬은 나머지 이벤트의 가장 유력한 잠재 구매자입니다.

**③ 응모형 상품이라 여러 개를 사는 것이 자연스러워요.**
LIVE MD는 당첨자 수가 정해진 응모 상품입니다(567번은 당첨자 10명, 중복 구매 가능, 최대 500개). 팬은 당첨 확률을 높이려고 이미 여러 장을 사요. 이벤트마다 경험이 달라서(영상통화, 팬사인, 게임, 꾸미기) "전부 응모"하려는 수요도 있습니다. 회차 내 가격이 전부 같아 추가 구매의 심리적 장벽도 낮아요.

**④ 판매 기간이 짧아서 나중에 알면 살 수 없어요.**
LIVE MD는 며칠만 판매하고 마감합니다(567번은 11/5 등록, 11/8 마감). 팬이 같은 아티스트의 다른 이벤트를 마감 뒤에 알게 되면 응모할 방법이 없어요. 팬이 직접 찾아내길 기다리기에는 기간이 짧으니, 처음 들어온 상세 페이지에서 바로 보여 줘야 합니다.

**⑤ 글로벌 팬 대상이라 상세가 길어요.**
안내문이 한·일·영 3개 국어로 반복되어 상세 영역이 깁니다. 하단에만 모듈을 두면 도달률이 낮을 가능성이 커요. 같은 아티스트 모듈을 구매 영역 바로 아래에 두는 이유입니다.

**⑥ 종료된 상세 페이지는 막다른 길이에요.**
마감 뒤에도 공유된 링크로 유입은 계속됩니다. 모듈이 없으면 "품절" 버튼만 보이고 갈 곳이 없어요. 이한결은 현재 6종이 모두 종료 상태입니다.

**⑦ 지난 이벤트 목록은 "다음에도 열린다"는 신호가 돼요.**
22팀 중 13팀이 2회차 이상 진행했습니다. 종료된 이벤트를 함께 보여 주면 이 아티스트가 이벤트를 반복해서 연다는 것을 알릴 수 있고, 이번에 놓친 팬에게 다시 방문할 기대를 줄 수 있어요. 판매 종료 상품을 카드에 포함하는 이유입니다.

### 2.3 주의할 점: 매출이 늘지 않고 나뉘기만 할 수 있어요

팬의 예산이 정해져 있다면, 한 이벤트에 5장 넣던 팬이 여러 이벤트에 나눠 넣을 뿐 총액은 그대로일 수 있습니다. 이 경우 교차 구매율은 오르지만 매출은 늘지 않아요. 그래서 교차 구매율과 **구매자당 결제액**을 반드시 같이 봅니다([6. 지표](#6-지표)).

## 3. 가설

모든 가설은 배포 전 회차의 지표와 비교해서 확인합니다.

| | 가설 | 확인 지표 |
|---|---|---|
| H1 | 구매 영역 아래에 같은 아티스트의 다른 상품을 보여 주면, 같은 회차 안에서 LIVE MD를 2종 이상 구매하는 구매자 비율이 배포 전보다 오릅니다 | 회차 내 교차 구매율 |
| H2 | 교차 구매는 예산 재분배가 아니라 추가 지출로 이어집니다 | 구매자당 결제액, 구매자당 구매 수량 |
| H3 | 상세 하단의 같은 카테고리 추천 모듈은 다른 아티스트 상품으로의 탐색을 만듭니다 | 모듈 2 클릭률, 타 아티스트 상세 조회율 |
| H4 | 판매 종료 상세 페이지에 모듈을 두면 이탈이 줄고 판매 중 상품으로 유입됩니다 | 종료 페이지 이탈률, 판매 중 상품 도달률 |
| H5 | 판매 종료 카드를 함께 보여도 원 상품 구매를 방해하지 않습니다 | 원 상품 구매 전환율 (가드레일) |

H3는 팬이 여러 아티스트를 동시에 좋아한다는 전제에 기대고 있어요. 그런데 LIVE MD 팬덤에서 이 전제가 성립하는지는 아직 근거가 없습니다. 이번 실험에서 처음 확인하는 항목이에요.

## 4. 노출 방안

### 4.1 검토한 위치

| 위치 | 장점 | 단점 | 채택 |
|---|---|---|---|
| **구매 영역 바로 아래** (옵션·구매 버튼 아래, 상품 정보 탭 위) | 구매 결정 시점에 보임. 도달률 높음 | 구매 버튼과 가까워 주의가 분산될 수 있음 | 이번 배포 — 모듈 1 |
| **상세 정보 하단** | 구매 흐름을 방해하지 않음 | 3개 국어 안내문 때문에 도달률이 낮음 | 이번 배포 — 모듈 2 |
| **장바구니 담기 직후 바텀시트** | 구매 의도가 가장 높은 순간. 담기 전환을 방해하지 않음 | 담은 사람에게만 보임. 판매 종료 페이지에는 적용 불가 | 추후 A/B 테스트 후보 |
| 옵션 영역 안 "다른 이벤트도 함께 담기" | 한 번에 여러 이벤트 담기 가능 | 상품마다 입력 정보 5개가 따로 필요해 구조 변경이 큼 | 후속 검토 |
| 장바구니 페이지 | 구현이 단순함 | 결제 직전이라 이탈 위험. 바로 구매 경로는 거치지 않음 | 후속 검토 |

### 4.2 모듈 1 — 같은 아티스트의 다른 상품

- **적용 범위**: 모든 카테고리의 상품 상세
- **위치**: 구매 영역 바로 아래 (상품 정보 탭 위)
- **제목**: `{아티스트명}의 다른 상품은 어때요?` (예: 장한음의 다른 상품은 어때요?)
- **대상**: 같은 아티스트(`brand.id`)의 전 상품. LIVE MD와 MD를 가리지 않고 모두 포함하고, 현재 보고 있는 상품은 제외해요
- **형태**: 가로형 상품 카드(`ProductCard` type=horizontal)를 3개씩 세로로 쌓은 열을 가로로 스크롤합니다. 최대 3열(3×3)이에요
- **최대 개수**: 9개
- **상품이 3개 이하일 때**: 열 하나를 좌우로 꽉 채웁니다(fill width). 가로 스크롤은 없어요
- **데스크탑**: 카드 한 장의 최대 너비는 400입니다
- **정렬**: 최신순. 판매 중 우선 정렬은 서버 작업이 필요해서 [남은 결정 사항](#9-남은-결정-사항)으로 둡니다
- **카드 구성**: 홈·목록에서 쓰는 공용 상품 카드를 그대로 씁니다
- **담기 버튼(+)**: 누르면 상품 옵션 바텀시트가 열려요. 판매 종료 상품에는 노출하지 않습니다
- **전체보기**: 해당 아티스트 페이지로 이동합니다
- **다른 상품이 없을 때**: 구좌 자체를 노출하지 않습니다 ([4.5 엣지 케이스](#45-엣지-케이스))

### 4.3 모듈 2 — 같은 카테고리의 추천 상품

- **적용 범위**: 모든 카테고리의 상품 상세
- **위치**: 상세 정보 하단 (상품 정보 아코디언 뒤, 푸터 위)
- **제목**: `함께 보면 좋은 추천 상품`
- **대상**: 현재 상품과 같은 1차 카테고리의 상품 전체(하위 카테고리 포함), 최신순. LIVE MD 상세에서는 LIVE MD 상품이 나오고, 현재 보고 있는 상품은 제외해요
- **형태**: 세로형 상품 카드(`ProductCard` type=vertical)를 가로로 스크롤합니다
- **최대 개수**: 10개
- **추천 탭**: 상세 탭(정보 · 배송 · 추천 · 문의)의 `추천`을 누르면 이 모듈 위치로 스크롤해요. 모듈 2가 노출되지 않으면 추천 탭도 숨깁니다
- **전체보기**: 해당 1차 카테고리의 상품 목록으로 이동합니다
- **중복 상품**: 지금은 모듈 1과 겹치는 상품을 그대로 보여 줘요. 제외하려면 서버 작업이 필요합니다 ([남은 결정 사항](#9-남은-결정-사항))
- **알아 둘 점**: LIVE MD는 한 회차가 3~4종씩 연속으로 등록되어 최신순에서는 한 아티스트가 카드 여러 장을 차지해요. 결과에서 쏠림이 보이면 "회차당 카드 1장"으로 묶는 안을 후속으로 검토합니다

### 4.4 판매 종료 처리

- **판매 종료 상세 페이지**: 판매 중 페이지와 똑같이 두 모듈을 노출합니다
- **판매 종료 카드**: 판매 중 페이지에도 함께 노출합니다. 공용 상품 카드의 SOLD OUT 딤으로 상태를 구분하고, 누르면 종료된 상세 페이지로 이동해요. 담기 버튼(+)은 숨깁니다
- **전부 종료된 경우**: LIVE MD 전체가 마감된 시기에는 모듈이 SOLD OUT 카드로만 채워져요. 이때 클릭이 막다른 길로 이어지지 않는지 가드레일로 봅니다

### 4.5 엣지 케이스

여기서 **히어로 노출 구간**은 모듈 1에서 스크롤하지 않아도 처음부터 보이는 카드, 곧 첫 번째 열의 3개를 말해요.

| 상황 | 처리 |
|---|---|
| 같은 아티스트의 다른 상품이 없음 | 모듈 1 구좌를 노출하지 않습니다. 제목과 여백까지 모두 빼서 빈 공간이 남지 않게 해요 |
| 모듈 1 상품이 3개 이하 | 열 하나를 좌우로 꽉 채우고 가로 스크롤을 없앱니다 |
| 같은 카테고리의 다른 상품이 없음 | 모듈 2 구좌를 노출하지 않고, 추천 탭도 숨깁니다 |
| 두 모듈 모두 상품이 없음 | 모듈 없이 기존 상세 화면 그대로 보여 줍니다 |
| 두 모듈의 상품이 겹침 | 지금은 중복을 허용합니다. 히어로 노출 구간과 겹치는 상품을 모듈 2에서 빼는 것은 서버 작업 여부가 정해진 뒤에 적용해요 |
| 현재 보고 있는 상품 | 두 모듈 모두에서 제외합니다 |
| 다른 상품이 전부 판매 종료 | 모듈을 그대로 노출하고 SOLD OUT 딤으로 구분합니다 |
| 목록 조회가 실패하거나 늦어짐 | 해당 구좌를 노출하지 않습니다. 구매 영역이 밀리지 않도록 자리를 미리 잡아 두지 않아요 |

### 4.6 구현 범위

두 모듈 모두 이미 열려 있는 공개 API로 조회합니다.

| 모듈 | 요청 | 비고 |
|---|---|---|
| 모듈 1 | `GET /v1/products?brandId={brand.id}` | 카테고리 조건 없이 아티스트의 전 상품 |
| 모듈 2 | `GET /v1/products?category={상품의 1차 카테고리}` | 하위 카테고리까지 포함해서 조회됨 |

- 목록 응답에 `isSelling`, `saleEndDate`, `price`, `mainImageId`, `brand`, `badges`가 들어 있어 카드에 필요한 값이 모두 있어요
- `category`는 하위 카테고리까지 포함해서 조회됩니다(`PCTGY3` → `PCTGY3_*`). `brandId`와 같이 걸면 두 조건을 모두 만족하는 상품만 나와요
- 카테고리 코드는 환경마다 다릅니다(운영 `PCTGY3`, 개발 `PCTGY12`). 코드를 직접 넣지 않고 상품의 카테고리 값을 그대로 씁니다
- 현재 상품 제외는 프런트에서 처리합니다

서버 작업이 필요해서 아직 적용하지 않은 항목은 두 가지예요.

| 항목 | 필요한 서버 작업 | 현재 상태 |
|---|---|---|
| 판매 중 우선 정렬 | 목록 API의 정렬 조건 추가 | 최신순으로 노출 |
| 중복 상품 제외 | 목록 API에 "제외할 상품 ID" 조건 추가 | 중복 허용 |

프런트에서 받아 온 뒤 거르면 모듈에 보이는 개수가 들쭉날쭉해져서, 중복 제외는 서버에서 하는 쪽이 맞습니다.

### 4.7 현재 배포와 최종 UI의 차이

1차 배포는 PRD와 다르게 나간 부분이 있어요. 이번 핸드오프에서 맞출 항목입니다.

| 항목 | 현재 배포 | 최종 UI |
|---|---|---|
| 적용 범위 | 모든 카테고리 상세 | 동일 |
| 모듈 1 제목 | `{아티스트}의 다른 상품` | `{아티스트명}의 다른 상품은 어때요?` |
| 모듈 2 제목 | `{카테고리}의 다른 상품` | `함께 보면 좋은 추천 상품` |
| 모듈 1 형태·개수 | 최대 5개 | 가로형 카드 3×3, 최대 9개 |
| 모듈 2 개수 | 최대 10개 | 동일 |
| 정렬 | 최신순 | 동일 (판매 중 우선 정렬은 결정 대기) |
| 카드 | 공용 상품 카드, 판매 종료는 Sold out 표시 | 공용 상품 카드 + 담기 버튼(+), 판매 종료는 SOLD OUT 딤 |
| 추천 탭 | 없음 | 추가 (모듈 2로 스크롤) |
| 전체보기 | — | 모듈 1은 아티스트 페이지, 모듈 2는 카테고리 목록 |
| 중복 상품 | 허용 | 동일 (서버 작업 결정 대기) |

## 5. 실험 설계

### 5.1 검증 방식 — 배포 전후 비교

이번 실험은 개선안(모듈 1 + 모듈 2 상세 기본 노출)을 **모든 방문자에게 배포**하고, 배포 전 지표와 배포 후 지표를 비교합니다.

이렇게 정한 배경은 다음과 같아요.

- 지금은 방문자를 나눠 서로 다른 화면을 보여 줄 실험 환경이 없습니다
- 서로 다른 시안을 비교하는 A/B 테스트는 실험 환경을 구축한 뒤에 진행하기로 했어요
- 서버 작업 없이 프런트 배포만으로 바로 시작할 수 있습니다

이 방식으로 알 수 있는 것과 없는 것을 미리 구분해 둡니다.

| 구분 | 내용 |
|---|---|
| 알 수 있는 것 | 모듈이 실제로 쓰이는지(도달·클릭), 클릭이 구매로 이어지는지, 교차 구매율과 결제액이 지난 회차 범위와 비교해 어느 수준인지 |
| 알 수 없는 것 | 지표 변화가 모듈 덕분인지, 아티스트·가격·상품 구성이 달라서인지. 같은 시기의 비교 대상이 없어서 원인을 단정할 수 없어요 |

그래서 이번 결과는 "효과가 확인됐다"가 아니라 **"방향이 맞는지"** 를 판단하는 근거로 씁니다. 원인까지 확인하는 일은 추후 A/B 테스트에서 진행해요.

### 5.2 단계

| 단계 | 내용 | 개발 |
|---|---|---|
| 0. 배포 전 기준선 확보 | 지난 회차의 교차 구매율, 구매자당 결제액 등을 뽑고, 기존 이벤트 로깅 상태를 확인합니다 | 없음 (데이터 추출) |
| 1. 전체 배포 후 측정 | 개선안을 전체 배포하고, 배포 후 한 팀의 회차를 측정해 기준선과 비교합니다. 1차 배포는 완료했고 최종 UI를 이어서 반영해요 | 프런트만 |
| 2. 시안 A/B 테스트 (추후) | 실험 환경을 구축한 뒤, 담기 직후 바텀시트 등 다른 시안을 나눠서 비교합니다 | 실험 환경 필요 |

### 5.3 비교 기준

배포 후에 측정하는 팀과 배포 전 회차의 아티스트는 서로 다를 수밖에 없습니다. 같은 아티스트끼리 맞춰 비교할 수 없으니, 배포 전 회차 전체를 하나의 기준선으로 써요.

- **배포 전 기준선**: 지난 LIVE MD 회차 중 상품이 2종 이상이었던 회차(현재 33회차)의 지표를 회차별로 뽑아 평균과 범위(최저~최고)를 정리합니다
- **배포 후 값**: 측정 대상 한 팀의 회차 값을 기준선의 평균·범위와 나란히 놓고 봅니다
- **참고용 비교군**: 기준선 안에서 측정 팀과 상품 수·가격대가 비슷한 회차를 따로 표시해 함께 봐요
- **배포 일시 기록**: 전후를 가르는 기준이므로 배포 일시를 문서에 남깁니다

기준선의 한 예로, 이한결 11.13 회차는 구매자 24명 중 9명이 2종 이상을 구매했어요(교차 구매율 37.5%).

### 5.4 대상과 기간

- **대상**: LIVE MD 상세 페이지 방문자 (판매 중·판매 종료 모두). 모듈은 모든 카테고리에 나가지만 판정은 LIVE MD 회차로 합니다. 판매 중 상품 방문자 기준으로 판정하고, 판매 종료 페이지는 따로 봐요
- **측정 기간**: 배포 후 **한 팀의 한 회차**를 기준으로 잡습니다. 그 회차의 판매 시작부터 마감까지 전체를 봐요
- **측정 대상 팀의 조건**: 동시에 판매하는 LIVE MD 상품이 2종 이상이어야 합니다
- **분석 단위**: 회차 안에서의 방문자·구매자. 팬이 주문을 나눠 넣을 수 있어서 주문 단위가 아니라 **구매자 × 회차** 단위로 봐요
- **중간 판단 금지**: 회차가 끝나기 전에 결과를 보고 결론 내리지 않습니다. 마감 직전에 구매가 몰리기 때문이에요

### 5.5 결과를 읽는 기준

한 팀의 한 회차만 측정하므로 통계적 유의성은 따지지 않습니다. 대신 배포 전 범위와 비교해 신호의 세기를 나눠 읽어요.

| 배포 후 값의 위치 | 해석 |
|---|---|
| 배포 전 최고값보다 높음 | 강한 신호. 지난 어떤 회차에서도 나온 적 없는 수준이에요 |
| 배포 전 평균보다 높고 최고값 이하 | 약한 신호. 방향은 맞지만 아티스트 차이일 가능성이 남아 있어요 |
| 배포 전 평균 이하 | 신호 없음. 모듈 도달률과 클릭률부터 확인합니다 |

측정이 한 팀에 그치는 만큼, 이후 회차에서도 같은 지표를 계속 쌓아 추세를 확인합니다.

## 6. 지표

### 6.1 지표 구조

클릭률과 연계 구매를 둘 다 보되 역할을 나눕니다. **판정은 교차 구매율로** 하고, 클릭률은 **왜 그런 결과가 나왔는지 설명하는 지표**로 써요. 이렇게 나누는 이유는 다음과 같습니다.

- 모듈 클릭률은 배포 전에는 모듈이 없어서 값이 존재하지 않아요. 배포 전후를 비교하는 지표가 될 수 없습니다
- 클릭은 많은데 구매는 안 늘 수 있어요. 판정 지표가 둘이면 결과가 엇갈릴 때 결론을 내릴 수 없습니다
- 실험 목표가 연계 매출이므로 판정은 구매로 합니다

지표의 출처도 둘로 나뉩니다. 구매 지표는 주문 DB에서 전부 집계되고, 방문·클릭 지표는 GA에서 봐요. GA는 분석 쿠키에 동의한 방문자만 잡혀서 실제 주문의 약 30%만 보입니다. 그래서 GA 기반 지표는 비율 위주의 참고용으로만 씁니다.

### 6.2 판정 지표 (1개)

| 지표 | 정의 |
|---|---|
| **회차 내 교차 구매율** | 한 회차에서 LIVE MD를 구매한 사람 중, 그 회차 안에서 서로 다른 LIVE MD 상품을 2종 이상 구매한 사람의 비율 |

- "구매자 × 회차" 기준으로 계산합니다. 나눠서 주문해도 한 사람으로 묶어요. 서버 작업은 필요 없습니다
- 회차 정보는 데이터에 따로 없어요. shop-chart > 실험실 > ④ 직접 비교에서 회차 상품과 기간을 골라 계산합니다
- 개인정보는 대시보드 서버 안에서 사람을 묶는 데만 쓰고, 화면에는 집계 숫자만 보여요

### 6.3 매출 확인 지표

교차 구매가 추가 매출인지, 재분배인지 가려내는 지표입니다. 판정 지표와 같은 기준(구매자 × 회차)으로 주문 DB에서 계산해요.

| 지표 | 정의 | 보는 이유 |
|---|---|---|
| 구매자당 결제액 | 회차 내 LIVE MD 결제액 합계 ÷ 구매자 수 | 교차 구매율만 오르고 이 값이 그대로면 재분배예요 |
| 구매자당 구매 상품 종류 수 | 회차 내 서로 다른 LIVE MD 상품 수의 평균 | 교차 구매의 깊이 |
| 구매자당 구매 수량 | 회차 내 LIVE MD 총 수량의 평균 | 종류는 늘고 수량은 그대로인지 확인 |

구매자당 결제액은 회차마다 상품 가격이 달라 그대로 비교하기 어려워요. 상품 가격으로 나눈 값(구매자당 구매 수량)도 함께 봅니다.

방문자당 LIVE MD 매출은 이번에 제외합니다. 방문자 수(GA)와 매출(주문 DB)의 출처가 달라서, GA가 주문의 약 30%만 잡는 상태로 나누면 결과가 왜곡돼요.

### 6.4 선행 지표

구매보다 빨리 쌓여서 방향을 먼저 확인할 수 있어요. 상세 조회·담기 이벤트는 배포 전부터 상품 ID와 함께 남아 있어서 배포 전후 비교 자체는 가능합니다. 다만 GA 표본이 작아서 판정 기준으로 쓰지 않고, GA 탐색 보고서에서 참고로 봅니다.

| 지표 | 정의 | 용도 |
|---|---|---|
| 교차 탐색률 | LIVE MD 상세 방문자 중 같은 세션에서 다른 LIVE MD 상세를 본 비율 | 참고 |
| 교차 담기율 | LIVE MD 상세 방문자 중 서로 다른 LIVE MD 2종 이상을 장바구니에 담은 비율 | 참고 |

### 6.5 진단 지표 (배포 후에만)

모듈 설계를 고치는 데 씁니다. GA4 이벤트로 보고, 표본이 작으므로 비율 위주로 읽어요.

| 지표 | 정의 |
|---|---|
| 모듈 도달률 | 상세 방문자 중 모듈이 화면에 들어온 비율 (모듈 1, 2 각각) |
| 모듈 클릭률 | 모듈이 보인 방문자 중 카드를 누른 비율 (모듈 1, 2 각각) |
| 카드 순서별 클릭 분포 | 몇 번째 카드가 눌리는지 |
| 판매 종료 카드 클릭 비중 | 전체 카드 클릭 중 판매 종료 카드의 비율 |
| 클릭 후 구매 전환율 | 카드를 눌러 도착한 상품을 구매한 비율 |
| 모듈 2 타 아티스트 구매율 | 모듈 2를 거쳐 다른 아티스트 상품을 구매한 비율 (H3 확인) |

### 6.6 가드레일 지표

배포 전 기준선과 비교합니다. 하나라도 기준을 벗어나면 원인을 먼저 확인하고, 필요하면 모듈을 내려요. 회차 간 편차가 커서 구체적인 기준값은 0단계에서 기준선을 본 뒤 확정합니다.

| 지표 | 정의 | 기준 | 출처 |
|---|---|---|---|
| 구매자당 구매 수량 | 6.3과 같음 | 배포 전 범위의 최저값보다 낮아지지 않아야 해요 | 주문 DB |
| 원 상품 구매 전환율 | 처음 들어온 상품을 구매한 방문자 비율 | 배포 전 범위의 최저값보다 낮아지지 않아야 해요 | GA (참고) |
| 원 상품 담기율 | 처음 들어온 상품을 장바구니에 담거나 바로 구매를 누른 비율 | 배포 전 범위의 최저값보다 낮아지지 않아야 해요 | GA (참고) |
| 결제 완료율 | 주문서 진입 대비 결제 완료 비율 | 배포 전 범위의 최저값보다 낮아지지 않아야 해요 | GA (참고) |
| 판매 종료 카드 클릭 후 이탈률 | 판매 종료 카드를 누른 뒤 바로 나간 세션 비율 | 판매 중 카드 클릭 후 이탈률의 1.5배 이내 | GA (참고) |
| 주문 취소·문의 건수 | 주문 1,000건당 취소 요청과 "잘못 응모" 유형 문의 건수 | 배포 전보다 늘지 않아야 해요 | CS 수기 집계 |
| 페이지 성능 | 상세 페이지 LCP, CLS | LCP 악화 200ms 이내, CLS 0.1 이하 유지 | 성능 측정 |

주문 취소·문의 건수는 CS 데이터라서 프런트나 대시보드에서 집계할 수 없어요. CS 문의를 수기로 집계해야 합니다.

주문 취소·문의를 보는 이유는 LIVE MD가 취소 불가 상품이기 때문입니다. 이벤트 카드가 서로 비슷해서 팬이 의도와 다른 이벤트에 응모하면 바로 고객 응대 문제가 돼요.

### 6.7 판정 기준

| 결과 | 결정 |
|---|---|
| 교차 구매율이 배포 전 평균보다 높고, 구매자당 구매 수량이 줄지 않았고, 가드레일 통과 | 모듈을 유지합니다. 이후 회차에서 추세를 계속 확인해요 |
| 교차 구매율은 높지만 구매자당 구매 수량이 그대로 | 재분배로 판단합니다. 매출 효과는 없지만 가드레일을 통과하면 유지해요 |
| 교차 탐색률·클릭률은 높은데 교차 구매율은 평균 이하 | 발견은 되지만 구매로 못 넘어가는 상태예요. 응모 정보 재입력 등 구매 단계의 마찰을 확인합니다 |
| 가드레일을 벗어남 | 모듈을 내리거나 위치를 아래로 옮깁니다. 판매 종료 카드를 빼는 안도 검토해요 |
| 모듈 도달률·클릭률 자체가 낮음 | 위치나 카드 구성 문제로 보고 모듈을 고칩니다 |

어떤 결과든 원인까지 확인된 것은 아니므로, 추후 A/B 테스트에서 다시 검증합니다.

## 7. 이벤트 로깅

별도 이벤트를 새로 만들지 않고 GA4 표준 이벤트를 씁니다. 모듈은 `item_list_name`으로 구분해요.

| 모듈 | `item_list_name` |
|---|---|
| 모듈 1 (같은 아티스트) | `pdp_artist_products` |
| 모듈 2 (같은 카테고리) | `pdp_category_products` |

| 처음 요청한 항목 | 적용한 방식 | 상태 |
|---|---|---|
| `related_module_view` | `view_item_list` — 모듈이 50% 이상 보일 때, 상세 페이지 1개당 1회 | 적용 |
| `related_item_click` | `select_item` | 적용 |
| `rank` | `index` (카드 순서) | 적용 |
| `target_is_selling` | `sale_status` (`on_sale` / `sold_out`) | 후속 배포 예정 |
| `target_brand_id` | `artist_match` — 보던 상품과 같은 아티스트인지 (`same` / `other`) | 후속 배포 예정 |
| `source_product_id`, `item_count`, `selling_item_count` | — | 이번 범위에서 제외 |
| `is_same_round` | — | 데이터에 회차 정보가 없어 미적용 |

모듈 카드로 들어간 상품을 담거나 결제하면 담기·결제 이벤트에도 같은 `item_list_name`이 붙습니다. 결제 쪽은 후속 배포 예정이에요.

기존 이벤트는 배포 전부터 남고 있습니다.

- 상품 상세 조회(`view_item`), 장바구니 담기(`add_to_cart`), 결제 완료(`purchase`) 모두 상품 ID를 포함합니다
- 결제 완료 이벤트에 주문 상품 목록과 금액이 들어 있어요

교차 구매율과 결제액은 GA와 무관하게 주문 DB에서 계산합니다.

## 8. 리스크

| 리스크 | 대응 |
|---|---|
| 아티스트·가격·상품 구성 차이를 모듈 효과로 착각할 수 있어요 | 결과를 "방향 확인"으로만 해석합니다. 상품 수·가격대가 비슷한 회차를 참고용으로 함께 보고, 원인은 추후 A/B 테스트에서 확인해요 |
| 한 팀만 측정해서 그 팀의 팬덤 특성이 결과를 좌우할 수 있어요 | 이후 회차에서도 같은 지표를 계속 쌓아 추세를 봅니다 |
| GA는 쿠키 동의자만 잡혀서 방문·클릭 지표의 표본이 작아요 | 판정은 주문 DB 지표로만 합니다. GA 지표는 비율 위주의 참고용으로 써요 |
| 판매 종료 카드가 많아 모듈이 "살 수 없는 상품 목록"처럼 보일 수 있어요 | SOLD OUT 딤으로 구분합니다. 판매 중 우선 정렬은 서버 작업이 정해지면 적용하고, 판매 종료 카드 클릭 비중과 이탈률로 확인해요 |
| LIVE MD가 전부 마감된 시기에는 모듈이 SOLD OUT 카드로만 채워져요 | 판정은 판매 중 상품 방문자 기준으로만 합니다. 이 시기의 문구는 [남은 결정 사항](#9-남은-결정-사항)에서 정해요 |
| 구매 버튼 근처 모듈이 원 상품 구매를 방해할 수 있어요 | 원 상품 전환율 가드레일로 확인하고, 벗어나면 위치를 내립니다 |
| 비슷한 카드 때문에 다른 이벤트에 잘못 응모할 수 있어요 | 공용 카드의 상품명 말줄임 규칙을 정하고([남은 결정 사항](#9-남은-결정-사항)), 취소·문의 가드레일로 확인합니다 |
| 상품마다 응모 정보 5개(이름, 생년월일, 전화번호, 카카오톡 ID, 이메일)를 다시 입력해야 해서 교차 구매가 중간에 끊길 수 있어요 | 클릭 후 구매 전환율로 확인합니다. 낮으면 직전 입력값 자동 채움을 후속 과제로 올려요 |
| 모듈 2가 다른 아티스트로 팬을 보내 원 아티스트 매출이 줄어들 수 있어요 | 원 상품 전환율 가드레일, 모듈 2 클릭 후 원 상품 복귀율을 확인합니다 |

## 9. 남은 결정 사항

| # | 항목 | 제안 |
|---|---|---|
| 1 | 판매 중 상품을 앞에 정렬할지 | 서버 목록 API에 정렬 조건이 필요합니다. 서버 작업 여부를 정해요 |
| 2 | 두 모듈의 중복 상품을 제외할지 | 서버 목록 API에 "제외할 상품 ID" 조건을 추가하는 쪽이 맞습니다. 지금은 중복을 허용한 상태예요 |
| 3 | 모듈 1 최대 개수 | 최종 UI 기준 9개(3×3). 후속 배포에서 10개로 늘리려던 계획을 9개로 바꿉니다 |
| 4 | LIVE MD 카드의 표기 기준 (배지 문구·색, 대괄호 이벤트명 말줄임 규칙) | 홈·목록에서 같이 쓰는 공용 카드라 바뀌는 범위가 커요. 디자인 기준을 먼저 정합니다 |
| 5 | 상품이 전부 마감된 시기의 모듈 문구 | 바꿔야 한다면 MD와 LIVE MD를 모두 아우르는 톤으로 다시 정리해요 |
| 6 | 측정 대상 팀 | 배포 후 처음 열리는, LIVE MD 상품 2종 이상인 팀의 회차 |
| 7 | 가드레일 기준값 | 0단계 기준선을 본 뒤 확정합니다 |
| 8 | 주문 취소·문의 건수 집계 담당 | CS 문의 수기 집계가 필요해요 |

## 10. 결정 이력

| 항목 | 결정 |
|---|---|
| 적용 범위 | 모든 카테고리의 상품 상세 (배포 완료) |
| 모듈 1 위치와 대상 | 구매 영역 바로 아래. 같은 아티스트의 전 상품(LIVE MD + MD) |
| 모듈 1 형태 | 가로형 카드 3×3, 최대 9개. 3개 이하면 한 열을 꽉 채움 |
| 모듈 2 위치와 기준 | 상세 정보 하단. 현재 상품과 같은 1차 카테고리 기준 최신순, 최대 10개 |
| 모듈 제목 | `{아티스트명}의 다른 상품은 어때요?` / `함께 보면 좋은 추천 상품` |
| 추천 탭 | 누르면 모듈 2로 스크롤. 모듈 2가 없으면 탭 숨김 |
| 전체보기 | 모듈 1은 아티스트 페이지, 모듈 2는 1차 카테고리 상품 목록 |
| 담기 버튼(+) | 누르면 상품 옵션 바텀시트 노출. 판매 종료 상품에는 숨김 |
| 판매 종료 페이지 | 판매 중 페이지와 똑같이 모듈 노출 |
| 판매 종료 상품 | 카드에 함께 노출하고 SOLD OUT 딤으로 구분 (추후 오픈 가능성을 보여 주기 위함) |
| 상품이 없을 때 | 해당 구좌 미노출 |
| 두 모듈의 상품이 겹칠 때 | 지금은 중복 허용. 제외는 서버 작업 결정 후 |
| 개발 범위 | 프런트만으로 배포. 정렬·중복 제외는 서버 작업 결정 대기 |
| 카드 | 홈·목록과 같은 공용 상품 카드 사용 |
| 이벤트 로깅 | GA4 표준 이벤트(`view_item_list`, `select_item`)와 `item_list_name`으로 대체 |
| 지표 | 연계 구매와 클릭률 둘 다 확인. 판정은 교차 구매율, 클릭률은 진단 |
| 방문자당 LIVE MD 매출 | 제외 (GA와 주문 DB의 출처가 달라 왜곡됨) |
| 측정 방식 | 개선안 전체 배포 후 배포 전후 지표 비교 (2026-11-11 변경) |
| 비교 기준 | 배포 전 회차 전체를 기준선으로 사용. 측정 팀과 아티스트가 다를 수밖에 없음 |
| 측정 기간 | 배포 후 한 팀의 한 회차 |
| 시안 A/B 테스트 | 실험 환경을 구축한 뒤 진행 |
